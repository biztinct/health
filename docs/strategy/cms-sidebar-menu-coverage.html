CMS sidebar coverage

Every menu our own modules ship that the /bizapp shell cannot reach, what it does, and where it could live. Measured on vietuat, 2026‑07‑29: 563 menus carry an action, 71 sidebar leaves cover 83 action xml‑ids, and 128 menus are reachable only by typing a URL.

Status, 2026‑07‑30 — table A is partly live. The CRM, OPERATIONS MANAGER, CLINICAL and FINANCE rows of table A shipped as health_cms_coverage 19.0.1.1.0: 19 leaves covering 23 menus, each one clicked in the shell before it was called done. Table A's ADMIN and ANALYTICS rows, all of table B and all of table C are untouched and remain open decisions. No existing sidebar item and no backend menuitem was modified or removed.

One correction the implementation forced on this document: it said visibility could be left to the model ACLs "because the underlying ACL still refuses the data". Driving the shell as the real crm user proved that too cheap — ungated leaves served a receptionist an entire FINANCE section their sidebar has never had, answering "You are not allowed to access 'BHYT Insurance Claim'" on click. The live catalogue turns out to gate 34 of its 71 leaves by access.role, written in the database (which is why the XML seeds look ungated), and the shipped leaves now follow each section's own convention: CRM → Owner + CRM, OPERATIONS → Owner + Operations Manager, FINANCE → Owner + Accountant, CLINICAL → ungated like its 24 siblings, with Voice Notes gated because only Owner / Operations Manager / Branch Manager can read health.scribe.job.

Why a menu can be invisible. A login lands in /bizapp, and /odoo redirects straight back into it — for the administrator too, which is how the operator‑only Platform Applications screen ended up URL‑only. The shell's app switcher lists only its own apps, so the whole CRM Center → … → Platform Applications path does not exist for any persona. That is ledger §5.69; the sidebar seed is the only fix.

Existing sections and their current size: CRM (9), OPERATIONS MANAGER (8), FINANCE (11), CLINICAL (24), INTEROP & COMPLIANCE (8), ADMIN (11).

Notes for whoever implements this

  • Leaves, not children. An item with children becomes a non‑navigating accordion — adding a child under an existing leaf silently stops that leaf opening (ledger §5.69a). New items go in as siblings with the next sequence.
  • Never set match_models on a satellite leaf. The model index is last‑wins, so a second leaf declaring crm.lead steals Contacts' highlight for every action without an xml‑id (§5.94). Declare match_action_xmlids only.
  • Visibility is by access.role, not by Odoo group. A leaf with no role_ids is shown to everyone; the underlying ACL still refuses the data, so an ungated operator leaf would show a link that errors. Platform Applications needs the Administrator role on the item as well as base.group_system on the model.
  • Removing a field from an XML data record does not unset it — write eval="False" explicitly (§5.69b).
  • The seed files live in health_cms_sidebar/data/, one per section, all noupdate="1"; a satellite module may ship its own (the health_cms_clinical pattern) rather than editing the base module.
