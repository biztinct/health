Order matters. bi.audit.log is append-only (unlink() raises — it is evidence)
and its user_id is a required Many2one, which PostgreSQL materialises as
ON DELETE RESTRICT, so a QA persona that merely runs a query becomes
undeletable through the ORM (§5.128). The raw, uid-scoped DELETEs therefore
run FIRST and in their own committed transaction (§5.142: an ORM unlink that a
later SQL error rolls back still prints as done — a cleanup script's own log
is not evidence that it cleaned anything).

$ psql -v ON_ERROR_STOP=1 -c "BEGIN; DELETE FROM bi_audit_log WHERE user_id=8625;
                              DELETE FROM ir_attachment WHERE id=83628; COMMIT;"
BEGIN
DELETE 9
DELETE 1
COMMIT

then, in an odoo-bin shell:  res.users(8625).unlink(); res.partner(20388).unlink()
  -> UNLINKED user 8625 partner 20388

Deliberately NOT deleted: bi_query_cache. That model sets _log_access = False
and has no create_uid at all — its columns are cache_key / created_at /
dataset_id / expires_at / hit_count / id / result_json (the very trap of
§5.142) — so there is no uid to scope a delete to. The rows are keyed by an
RLS fingerprint that includes the now-deleted uid, hold no personal data, and
expire on a 60-second TTL for a live dataset.
