## Phase plan

### GA0 — establish current facts

- Inspect git branch/status and relevant instructions; record changed files from other sessions.
- Read the design, complete conventions, channel architecture, current website handovers and SaaS runbook.
- Identify exact manifests, UI inheritance IDs, current lookup model fields, company/area rules and CRM→Care Command hooks.
- Locate the real website relay source and host; audit `gclid`, `wbraid`, `gbraid` and campaign fields through each hop.
- Discover current deployment inventory and Google reporting configuration without printing secrets.
- Recheck the native-form healthcare restriction and current supported Ads API version.

Exit: file-impact list and test/target inventory recorded. Missing external credentials are explicit, not a reason to invent them.

### GA1 — card and website acquisition

- Add `health_google_ads`, minimal Center extra-card hook and external-action dispatch.
- Implement account draft and capability-level state; add website connector links and honest native restriction copy.
- Add attribution extension fields and website optional payload handling; fix proven missing braid persistence.
- Implement company-safe account/campaign matching and source filters; preserve first touch and lead merge rules.
- Implement synthetic server and website round-trip evidence without production test leads.
- Add EN/VI UI and source-detail views; verify Care Command visibility through the existing hook.

Exit: GA-T01–11, GA-T19–21 applicable checks pass. Actual website setup is verified or explicitly recorded as awaiting its owner.

### GA2 — reporting authorization

- Add encrypted platform/account credentials and bound single-use OAuth sessions.
- Implement customer discovery including manager/child access, explicit selection and access validation.
- Add refresh locking, reconnect/disconnect and safe errors; isolate reporting failures from capture.
- Use a fixed-host API client with read operations only; no ad mutation services.

Exit: GA-T09, GA-T12–14, GA-T18–19 pass. Record the selected supported API version and actual authorization status.

### GA3 — reporting cache and metrics

- Add campaign/day models, uniqueness constraints, exact micros handling and account timezone/currency.
- Add complete-window staging/upserts, pagination, backoff and deduplicated sync jobs.
- Implement §8 metrics, mapping review, freshness and access-safe aggregates.
- Verify new-enquiry counts versus merged touches and distinct Google conversion totals.

Exit: GA-T15–17 and GA-T22 pass; failed sync cannot erase known good reporting data.

### GA4 — release and end-to-end verification

- Re-read latest branch, preserve combined state and commit scoped implementation.
- Deploy current combined code to all in-scope databases and the website relay where changed.
- Run appropriate real Odoo transaction/HTTP tests; ensure HTTP suites actually executed.
- Run the deployed Chrome flow in design §12 with operator and restricted-user personas.
- Verify template install/provisioning, disabled template jobs, absent template secrets, existing channels and website regression path.
- Remove only PNGs/screenshots generated by this test run. Record textual evidence and deployment report.

Exit: commit, targets, test outcomes and real capability status reported. Missing live Google/website setup is a named blocker, not a fabricated connected state.

### GA5 — conditional native forms, separately requested

- Recheck eligibility; do not enable healthcare lead-form ads contrary to Google's policy.
- Implement design §10 form binding, key lifecycle, durable receipt endpoint and asynchronous processing.
- Integrate provider-neutral dedup/routing without spoofing the WordPress schema or consent.
- Implement receipt review/retry, non-chat timeline event, retention and all GA-N tests.
- Verify an actual eligible saved form's Google test delivery plus controlled live acceptance where authorized.

Exit: independently deployed and verified native capability. Historical API backfill and conversion uploads remain separate follow-on designs.

## Decisions an implementer must not silently reverse

- Google Ads is an acquisition card, not a new reply transport.
- Website capture does not depend on reporting OAuth being healthy.
- A click/aggregate conversion is not an identifiable person or CRM lead.
- Customer/campaign IDs remain strings; company access never comes from payload IDs.
- First-touch attribution is immutable on ordinary follow-up merges.
- Native healthcare forms remain unavailable; a successful webhook test cannot grant eligibility.
- Test deliveries do not contaminate CRM counts or trigger outbound messages.
- Document-only design work requires no application deployment; subsequent implementation does.
