As written on 3 September

The short answer

No — a change in master should never land on every customer at once, and world-class SaaS companies go to great lengths to make sure it doesn't. They ship the code everywhere, then turn it on in small groups over days, watching for damage between each group.

Our setup is architecturally right: one copy of the product on the server, one database per customer, and a screen that decides who gets what. That is the same shape the state of the art uses. What we are missing is the machinery around it — version numbers, groups, a switch to hold a feature back, an alarm, and a way to undo.

There is also one thing about our setup that is not what we think it is, and it matters more than everything else on this page:

The finding

When we change the product's behaviour and deploy it, every customer gets that new behaviour at the next restart, whether we chose it or not. Only the new screens and data wait for someone to press a button per customer. So the risky half travels automatically and the safe half is manual — the exact opposite of what it should be. Today we have three customers and it is survivable. At thirty it is a very bad night.

And the promise on our own Tenants screen — "every customer gets what the master gets" — is currently only half kept. It gives a customer modules they don't have. It never updates the ones they already have. A customer can sit thirty versions behind on the payroll engine and the screen will say they are in step.

Reality check, as it was on 3 September

What happened before the programme

A change to the master is not one thing. It is three, and they travelled at three different speeds. Layers 2 and 3 are now handled by the release and rollout machinery; layer 1 still travels at restart, which is why the rule "the master is upgraded first" and the rehearsal wave exist.

1 · Behaviour — the calculations, the buttons, the screens' logic

Reaches everyone automatically

All customers share one copy of the product on disk. The moment we deploy and the server restarts, every database is running the new logic. Nobody chose this per customer. Nobody can hold it back for one customer. There is no version to point at.

2 · Screens, settings and data structure

Only when we run the update, per customer

New fields, new menus, new default records. These wait until someone runs the update command against that specific database. Until then that customer runs new logic against an old shape — which is the single most common way a fleet breaks.

3 · Whole new modules

Only when someone presses Sync on that customer

This is the part we built and it works well: the screen lists what a customer is missing, holds back the four platform-only parts with a reason, and installs the rest on one press.

This has already bitten us once

On 19 August, twenty-seven modules quietly stopped loading on the customer databases. Cause: master gained two new modules, other modules were changed to depend on them, and that dependency change travelled instantly (layer 1) to databases that had never been told the new modules existed (layer 3). Nothing showed as broken — the module list still said "installed" — until two background jobs started failing every five minutes. That is the hybrid failing, exactly as described above.

The benchmark

How world-class SaaS actually ship

Salesforce, Shopify, Atlassian, GitHub, Workday and every serious payroll vendor differ enormously in their plumbing, but they all obey the same six rules. None of them is exotic; all six are missing from our platform today.

  1. Deploying is not releasing

    Code goes out to everyone, switched off. A feature is opened to customers afterwards — by flipping a switch per customer or per group, with no deploy involved. This is why a big company can ship fifty times a day and still control what customers see. We have no switch, so installing a module is our release, and it is all-or-nothing.

  2. Every customer has a version number, and we know it without looking

    "Acme is on release 2026.09.1" is a field on the customer record, not something you find out by logging into a server. Support, sales and engineering all read the same number. Ours does not exist.

  3. Changes move in waves, never in one go

    Internal first, then one willing customer, then a small slice, then the rest — with a pause between each wave and a rule for stopping. Salesforce famously upgrades its customers in scheduled waves and gives them a preview environment weeks beforehand. Shopify and GitHub call them rings. Nobody flips 100% at once.

  4. New code must work on the old data shape

    This is the discipline that makes waves possible at all. Add the new column, keep the old one working, migrate, then remove the old one in a later release — never in the same one. Without it, the gap between "code deployed" and "this customer updated" is a broken customer. Right now every one of our deploys opens that gap and we simply close it fast by hand.

  5. Updating a customer is a queued job, not a person at a terminal

    It can be retried, it holds a lock so it can't run twice, it puts a banner up for that customer's users, it records how long it took, and it reports success or failure to a dashboard. Ours is an SSH loop in a runbook, run by whoever is awake.

  6. Undo is rehearsed, not hoped for

    Before a wave, a real customer's backup is restored to a scratch copy and the update is run there first. If the wave goes wrong, the restore path is one that somebody has actually walked this quarter. We built the scratch-restore button — good — but we have never proved a restore end to end, and the backups sit on the same machine as the thing they protect.

Where our shape is genuinely fine

One database per customer is not second-best. It is what payroll, health and finance vendors choose deliberately: a customer's data cannot leak into another's through a forgotten filter, one customer can be restored to yesterday without touching anyone else, and a big customer can be moved to their own machine later without a rewrite. The trade is that upgrades are per-customer work — which is precisely why the machinery above exists.

Priorities

The gaps, ranked by what they cost us

Ranked by damage if ignored, not by effort.

1 · Backups are on the same machine as the thing they protect

Not started

If that machine is lost — hardware, a bad command, a compromised account — we lose every customer's payroll history and every backup of it in the same second. There is no second copy anywhere.

Fix: copy each nightly backup off the box to object storage (S3 or equivalent) with encryption and a lock that prevents deletion for 30 days. Half a day of work. Do it this week.

2 · No restore has ever been proved

Not started

An untested backup is a belief, not a backup. We do not know how long a restore takes, whether the attached files come back with it, or whether the result actually starts.

Fix: restore one customer to the scratch copy, log in, open a pay run, and write down the elapsed time. Repeat quarterly, recorded on the customer's record. Half a day.

3 · Sync adds modules but never updates them

Done

The screen compares names only. A customer running last quarter's payroll engine shows as "in step". We have already seen one customer thirty-eight versions behind while the screen was green.

Fix: compare versions too, show "behind by", and add an Update action beside Install. Two to three days, and it makes the promise on the screen true.

4 · No version number per customer

Done

Nobody can answer "what is Acme running?" without logging into a server. Support cannot reproduce a bug. We cannot say what a fix will reach.

Fix: a release stamp on the customer record, written by the update job. One day, and it unlocks everything in the next section.

5 · Nothing wakes a human

Done

A customer's site can be down, a backup can fail every night, a background job can error every five minutes — and we find out when we open the screen or a customer calls. That is the difference between an incident and an embarrassment.

Fix: send failures to email and one phone (any paging service, or just a Telegram bot to start). One day.

6 · No way to hold a feature back

Done

Everything we build reaches everyone the moment it is deployed. We cannot pilot a feature with one customer, cannot sell a premium tier, cannot turn something off when it misbehaves without a code deploy.

Fix: a simple switch table per customer, read by the screens. Three to four days, and it is the single highest-leverage thing on this page.

7 · No plan, no seats, no billing, no suspend

Done

Today growth means more manual work and no automatic money. A customer who stops paying cannot be closed without deleting them.

Fix: plans and staff limits first, then a suspend state, then card payment. Two to three weeks, and it is the difference between a platform and a product.

8 · The memory ceiling

Done

1.9 GB holds a working copy of the product for every customer being used at that moment. Somewhere around five to eight active customers this stops being a slowdown and starts being outages.

Fix: move to a 8 GB machine before the fourth paying customer, and separate the database onto its own service when we pass ten. Planned, not reactive.

9 · No customer-visible communication

Done

No maintenance notice, no status page, no "what's new". Restarts look like faults to the people using the product.

Fix: a banner triggered from the Tenants screen and a one-page public status page. Two days.

10 · Support access without a trail

Done

We will need to look at a customer's data to help them. Doing it through the break-glass admin leaves no record of who looked at what, which is the first question a payroll buyer's security review asks.

Fix: a "view as customer" action from the Tenants screen that writes an entry the customer can see. Two to three days.

11 · No sandbox per customer

Not started

Payroll customers want to try a change against their own real data before running it for real. Every serious payroll vendor offers this, and we are one button away from it — the clone and restore machinery already exists.

Fix: "Create sandbox" = restore last night's backup to <slug>-sandbox, with a coloured banner. Two days, and it is a genuine selling point.

The one structural idea to adopt

Introduce a Release: a dated, named set of module versions that customers move onto as a unit. Once a release exists as a record, everything else in wave B falls out of it naturally — a customer's version is which release they are on, a wave is which customers move next, a rollback is the previous release, and a changelog is what the release contains. Without it, every one of those has to be invented separately.

Free wins

Rules to adopt now, before any code

These cost nothing and prevent most of what goes wrong on a fleet.

  • New code must work on the old data shape. Add, don't replace; remove the old thing a release later. This is what makes staged rollout possible.
  • Never make one module depend on another without touching every database. Our 19 August incident was exactly this. Adding a dependency is a fleet-wide job, not a single-database change.
  • The golden template is upgraded first, never last. A template behind the master silently creates every new customer already out of date.
  • Rehearse on a scratch restore of a real customer before the first real one. We have the button. Use it every time, not when it feels risky.
  • One named canary customer, who knows they are first, and a fixed watch period before anyone else moves.
  • After every deploy, check three things per database: the module versions match, no modules were skipped at startup, and no background job errored in the following fifteen minutes. All three are in the runbook already.
  • Never deploy on a Friday or on a customer's pay day. Payroll has a calendar; use it as the release calendar.

For engineers

Appendix — the technical facts behind this

Verified against the working tree on 3 September 2026, branch 19.1.

Why layer 1 travels automatically

addons_path is a single shared tree (/odoo/odoo-server/addons) and one server process serves all databases via dbfilter = ^%d$. Python and JS are loaded from that tree at registry build, so any restart picks up new code for every database at once. Only XML/data/schema and ir_module_module state are per-database, requiring -u. True per-cohort code versions would need separate worker processes with their own addons_path, routed by nginx upstream — worth costing when the fleet passes ~10 tenants, not before.

The sync gap, precisely

sync_split() in pb_tenants/models/service.py:196 computes set(master) - set(tenant) over module names; _installed_on() (line 1102) selects name FROM ir_module_module WHERE state='installed'. Neither reads latest_version. There is no call to button_immediate_upgrade anywhere in the module. Adding drift detection means selecting (name, latest_version), normalising the 19.0. series prefix as the deploy contract already requires, and adding an upgrade action beside sync_install.

State machine gaps

pb.tenant.state is draft/provisioning/live/error/decommissioned. A commercial platform needs at least trial, suspended and pending_deletion with a retention clock, plus release_id, plan_id, seat_limit and sandbox_of.

Known constraints already documented

Memory ceiling (1.9 GB, registry per served DB), the manual DNS-01 wildcard certificate that does not auto-renew, the pb_explorer fact builder that cannot run without pb_demo's column, and the analytics cleanup job with the fields NameError — all in docs/SAAS_RUNBOOK.md under Known debt. The first two are fleet-wide risks and belong in wave A.
