Why the singles lose, specifically here

A — Journey only. Cheapest and fastest, and it does teach the map. But CRM's damage is done by actions, not by ignorance of where a menu is. Nothing in a lesson stops an operator sending a clinical detail to a family member whose consent was withdrawn. Watching is not deciding.

B — Simulator only. The strongest single surface for judgement, and it carries the two things that matter most (consequence interception, seeded anomaly). But it is useless as a reference at 07:43, teaches nothing about the five screens with no risky action, and is the most expensive thing to build first.

C — Companion only. Best marginal value per pound and the only one that helps the Nurse and Ops roles, who need three answers a month, not a course. But an answer engine cannot give someone a mental model they have never had, and “ask a question” is exactly what a nervous new operator will not do.

D — Staged hybrid. Wins because the three surfaces cover each other's blind spots and — this is the part that makes it affordable — they consume one content spine. The urgency arithmetic is authored once and appears as a lesson step, a coach calc-block and a mission fact. Three separate content systems would cost roughly triple to keep in two languages; this costs one.

Recommendation: build D, in the order Journey → Companion → Simulator. Journey first because it ships value in one phase and forces the content spine to exist. Companion second because it reuses that spine almost for free and is what actually deflects tickets. Simulator last because it is the most expensive and it depends on both.

The two seeded anomalies

M1 — the tempting answer is the wrong one. Conversation #4172 screams urgency: score 110, a watch phrase, a missed call, a visit in eight hours. The message asks a clinical question. The Zalo account belongs to the patient's daughter, and the patient withdrew her Data Sharing consent for that daughter in June. Speed and permission are different questions, and only one of them can be undone. The correct path is still fast — acknowledge, don't disclose, escalate, and call the client's own number.
M2 — every check passes and it is still wrong. Re-authorising the Hà Nội Zalo connection, the provider returns both Official Accounts sorted by creation date, so TPHCM is listed first. Choose it and all four readiness checks still pass: the connection is perfectly healthy and pointed at the wrong city. No error, no warning — the Hà Nội desk simply has a quiet week while TPHCM drowns.

§5Phased roadmap

Phase 0Prototype — done

This artifact. Proves the interaction quality, the bilingual parity and the content schema on real inventory and real arithmetic.

Phase 1Content model + anchor lint + Journey (≈ 5 weeks)

The phase that makes everything else cheap.

  • A translatable carejiox.learn.content model with the schema in data.js; exported to the frontend as JSON; one record per station, lesson step, quiz, mission and coach intent.
  • Anchor registry + CI lint — data-a="…" on every referenced control; the lint fails the build when content names an anchor no template has. Do this first or the system rots within two releases.
  • Journey map + the two flagship lessons + six outlines, both languages, progress, resume, reduced motion.
  • Ship to CRM/Reception users in one catchment area first.

Phase 2Care Coach on the same spine (≈ 4 weeks)

Highest deflection per unit of work, because the content already exists.

  • Dock on all eight CRM screens; retrieval grounded on the Phase-1 records only.
  • Rich-answer blocks (steps with point-at, calc breakdowns, warn/ok callouts, source line).
  • Role-aware answers wired to the real access.role rows and the CRM manager group — including honest refusals for Nurse and Ops.
  • Binding honesty rules enforced in code: never claims to have acted, never invents a price/rate/clinical fact, fallback states what it can answer.
  • Always-on, not a destination: a persistent launcher on every in-scope screen plus a ? shortcut, opening a drawer that does not dim or block the screen behind it. You reach for it because you are stuck on that screen, so the screen has to stay readable.
  • One resolver seam so an LLM can be plugged in later (answered in §9) without touching the content spine or the honesty rules. Retrieval stays the default, because it is what lets the Coach promise never to invent a fact.

Phase 3Practice Clinic + personalisation (≈ 6 weeks)

  • No practice tenant needed (answered in §9): the practice clinic is the versioned JS fixture, which is structurally incapable of touching production because there is no server behind it. The banner became the last line of defence rather than the only one — and Phase 3 lost its biggest cost driver.
  • Mission engine driving the real screens through the anchor registry.
  • M1 and M2 first, then M3/M4 and one Dashboard-reading mission. 5–8 total, never one per menu item.
  • Starting modes, struggled-twice → simpler explanation + practice hand-off, confidence scoring.

Phase 4Extend to OPS / CLINICAL / FINANCE + optimisation

  • Same spine, new lines on the same map. Marginal cost per section falls sharply.
  • Abandonment funnels, question clustering → new content, quiz-item analysis, EN-vs-VI comprehension deltas, ticket deflection.

§6Success metrics

Decision: a self-referential baseline. Month 1 is the reference period. There is no onboarding history and no ticket record, and manufacturing a control group by withholding training from the first cohort would be both slow and wrong. So: instrument on release day, treat month 1 as the baseline, and set every relative target against it from month 2 onward. The provisional numbers below exist so the team has something to steer by from week one — they are stated assumptions, and each is replaced by a measurement after four weeks.

The two safety metrics are the exception: they are absolute from day one, because "fewer consent breaches than last month" is not a standard anyone should accept.

The only hard requirement this places on Phase 1: the event log ships in release 1, not release 4. It is a handful of event types, and if it slips, the pre-tutorial reference period is gone permanently.

Two content-quality bands — these judge the material, not the learner

  • Quiz first-try correctness, per item: healthy band 50–80%. Above 80% the question is teaching nothing and should be replaced. Below 50% it is ambiguous or unfair, not hard. Either way the item is the problem.
  • Mission recovery-dialog frequency: healthy band 30–70%. Below 30% the seeded anomaly is too obvious to be worth seeding. Above 70% it is a trap rather than a judgement. Zero is a failure, not a success — it means nobody is being taught anything they did not already know.

Primary — establish first, then improve

  • Time to first correctly-handled urgent conversation for a new CRM operator (claim → appropriate reply → correct disposition), unsupervised. Establish.
  • Consent-breach near-misses — replies containing clinical content sent to a non-patient account. The one metric with an absolute target from day one: zero, measured by sampling.
  • Mis-routed channel incidents per quarter (a connection pointed at the wrong catchment area). Currently invisible until someone notices a quiet week — so instrumenting it is itself a win, independent of the tutorial.
  • Duplicate client records created per 100 bookings. Establish.
  • Question-type support requests per active CRM user. Establish over four weeks, then target a reduction.
  • Self-service resolution rate — a coach answer not followed by a ticket in 24h. Measurable from the first release, since both sides are instrumented by us.

Secondary

  • Lesson completion and the exact step where people abandon.
  • Quiz first-try correctness per item — a question everyone gets right is teaching nothing.
  • Mission recovery-dialog frequency. Healthy is above zero: nobody ever hitting the seeded anomaly means the anomaly is too obvious.
  • Confidence score vs. supervisor sign-off — do they agree?
  • Repeat coach visits per user per screen (should fall for the same user, stay flat across new users).
  • EN vs VI completion and comprehension delta. A gap means the Vietnamese is machine-literal somewhere.
  • Anchor-lint failures per release — the leading indicator of tutorial rot.

§7Integration checklist into the real product

  1. Anchor registry first. Add data-a to every control the content points at, starting with Care Command's wall rows, claim banner, action strip and composer, and the Channel Center's connection cards and readiness panel. Then the CI lint.
  2. Content model. carejiox.learn.*, translatable fields, shipped as module data files with noupdate="0" (§8), delivered to the browser as one ETag-cached JSON bundle per language. Port data.js's shape verbatim; replace nothing but the delivery mechanism.
  3. Practice fixture stays a static asset, never ORM records (§8), and check_contract.py runs in CI beside the anchor lint.
  4. Mount the Coach launcher in the CMS shell, not per screen — that is what makes it present everywhere for free, and it is the only mount point that survives new screens being added.
  5. Reuse the real gates. Read visibility from cms.sidebar.item.role_ids and permissions from group_health_crm_user / group_health_crm_manager. Do not re-declare a second role model for the tutorial — it will drift.
  6. Mount points. The Journey belongs in a new sidebar leaf; the Coach dock belongs in the CMS shell so it is present on every in-scope screen without per-screen work.
  7. Vietnamese labels. The tutorial must read menu labels from the same translated records the sidebar renders, never from its own copies, or the two will disagree after the first rename.
  8. Translate the four untranslated CRM strings (below) before Phase 1 ships — a learning system that names a menu item the sidebar does not is worse than no learning system.
  9. Practice tenant isolation. Separate company, no channel credentials, outbound adapters stubbed at the service layer. Prove with a test that a practice-tenant send raises rather than sends.
  10. Progress storage. Per-user records, not localStorage; keep the same state shape so the prototype's resume/badge logic ports unchanged.
  11. Accessibility gate in CI. Reduced-motion, keyboard path through the lesson player and quiz, aria-live narration, visible focus. The prototype passes all four; keep it that way.

§8Where this is installed, and where the data lives

Settled after the open questions in §9 were answered. These are decisions, not options.

What tenancy actually is here

Tenancy is res.company inside one Odoo database, not database-per-tenant. Two structural facts decide everything below:

  • cms.sidebar.item has no company_id — navigation is database-global, gated only by role_ids.
  • access.role has no company_id either — roles are global, attached to users by many2many.
  • Only transactional models (care.conversation, watch phrases, reply templates) carry company_id. Data is company-scoped; configuration and navigation are not.

Recommendation: installed in every tenant, authored centrally, no master training tenant

The rule that makes this robust: never make tutorial content a tenant-editable record set. If content is authored in a database, one tenant ends up holding "the good version" and the rest silently drift — and the anchor lint cannot guard what it cannot see. Ship content in the module; Product controls it by release. The single concession is a small, explicitly-scoped override table for genuinely local facts (a clinic's own hotline number, its escalation names). The moment it can override a lesson step, you have a fork.
Keep the training tenant — for a different job. Sales demos, an onboarding day where someone clicks around a realistic system with consequences they don't own, and release rehearsal where Product exercises new content against real screens before shipping. That is a demo/sandbox environment, complementary to the in-app system. "Both catchments see the same data" belongs there as configuration — not in the product.

Two things to watch

  1. If you later split to database-per-tenant — likely when you sell to multiple clinics — this design survives unchanged, because content travels in the module rather than in tenant data. That robustness is the main reason to choose it now, while it is still cheap.
  2. When a second real clinic joins this database, the Training leaf appears for everyone (correct), but tenant-specific content has nowhere to live, because the sidebar has no company_id. Design the override table before the second tenant, not after.

Two traps from this repo that apply directly to the content model

  • Content data files must be noupdate="0", so every upgrade rewrites them. This repo's own noupdate seed-cutover gotcha is exactly this failure: edit a noupdate="1" record and the upgrade silently does not apply it.
  • Any Selection on the content model must use the callable env._() form. Static lists and jsonb writes do not translate here — measured in this codebase.

Delivery to the browser: one controller endpoint returning the whole bundle as JSON, cached with an ETag keyed on module version + language. Not N queries per screen.

Keeping a fixture honest without a tenant

A fixture drifts. That cost is paid by contract.json — which declares every fact the tutorial asserts, where it came from, which fixture entries hold it and which lessons quote it — plus tools/check_contract.py, which re-reads the addons and fails when a declaration stops holding. 21 checks today, covering the urgency weights, four selection sets, the sidebar inventory, the shipped Vietnamese labels, the role gate, and the anchor registry.

Verified by breaking it on purpose. Re-weighting the watch-phrase term from 15 to 25 in the real model made the checker fail and name CASE.urgency plus the six pieces of content that quote it. Translating "Care Command" in the .po made the known-gap check fail with "GOOD NEWS: … update MENU and delete this entry". The addons were restored afterwards.

The first version of the check was presence-only and stayed green through the re-weight, because score += 15 appears twice and the other one still matched. It now asserts exact occurrence counts — which also fires when a new term is added, as it should.

§9Assumptions, findings and answered questions

Findings worth acting on regardless of this project

“Care Command” ships untranslated. health_care_command/i18n/vi.po carries msgstr "Care Command" for the sidebar item, the client action and the menu. Vietnamese-speaking operators see an English product name for the screen they live in all day. Three sibling strings in the same section — Dashboard, Contacts, Activities — are translated. The prototype keeps the shipped label rather than inventing one; it should be translated in the product, and the tutorial will follow automatically once it reads the same records.
The CRM section's role gate is invisible in the source. Because access.role rows have no xml-id, the gate is written in Python and cannot be read from the XML seeds. Anyone reasoning about “what does a receptionist see” from grep role_ids will get the wrong answer — as we nearly did, until the live sidebar was checked. Worth a comment in the seed files pointing at the hook.

Assumptions made (each one is cheap to correct)

  • The worked case is invented, the arithmetic is not. Nguyễn Thị Hoa, her daughter, the 08:00 Wednesday timestamp and the August figures are fictional; every calculation over them follows the real code. The month reconciles: 224 enquiries = 14 spam + 210 real; 210 = 63 booked + 129 leads + 18 lost; conversion 63÷210 = 30.0%; spam 14÷224 = 6.3%; the six source channels sum to 224.
  • Prices are illustrative. 450.000 ₫ for a 60-minute home wound-care visit and 3.400.000 ₫ for the 8-visit package are placeholders. The coach explicitly refuses to quote a real price, and says why.
  • Four roles in the switcher (CRM, Nurse, Ops, Owner) out of the nine that exist — the four whose CRM experience differs. Branch Manager, Banker, Doctor, Accountant and Admin behave as one of these four for this section.
  • “CareJioX” is used as the product name per the brief. The repository and the live deployment brand as Viet Uc Care / CMS Việt Úc. One search-and-replace either way.

Answered — and what each answer changed

Is there a practice/demo tenant? No. Use JS-based sample data instead — but keep the flexibility to update the tutorial when code or the data model changes. Practice data became practice-data.js, a versioned fixture, and the screens now render from it rather than from literals. The drift cost is paid by contract.json + check_contract.py (§8), which names the fixture entries and the lessons to update when a check fails. Phase 3 loses its biggest cost driver.
Who owns content after launch? Product. Content ships in the module and is controlled by release, not edited per tenant. Confirms the rule in §8 and removes any need for an in-app content editor in Phases 1–3.
What is the onboarding baseline today? New company — unknown. The "−40% on tickets" target was unmeasurable, so §6 no longer claims it. Phase 1 now establishes the baseline in its first four weeks, and targets are set against that.
Are the VI labels authoritative in .po or the database? Both are in sync. No production yet; it follows data cleanup and migration. Removed as a risk for now, but the divergence remains possible under this repo's noupdate seed-cutover pattern — so the contract check asserts the shipped .po strings, and the tutorial must read whatever the sidebar reads. Pre-production is also the cheapest moment to translate "Care Command".
LLM-backed Coach, or retrieval? Retrieval for now, with the widest coverage possible — and pluggable into an LLM later if needed. The Coach keeps its guarantee that it never invents a fact. Its retrieval is being widened, and the answer path is being isolated behind a single seam so an LLM can be dropped in without touching the content spine or the honesty rules.
Which cohort ships first? Any one catchment area is enough; for demo both areas may see the same data. Phase 1's rollout is unblocked. The relaxed catchment scoping is demo-environment configuration and stays out of the product (§8).
