A04 — Encryption and key custody

Design before implementation; accepted test evidence will be generated only after a fix is in place.

Components

health_phi_encryption, biz_tenants

Requirement coverage

EV-01-4, EV-04-1, EV-09-1

Expected application exhibit

Read-only encryption coverage/health summary, never secret keys or plaintext patient data.

Verification and negative cases

Inspect DB, filestore, audio, temporary/export copies, replicas and backups. Verify TLS, encrypted artifacts, legacy migration, separation of keys, rotation and controlled recovery.

Artifacts after implementation

A04-storage-coverage.csv; A04-TLS-report.pdf; redacted key/rotation records; migration results; encrypted-backup and recovery test report.

Review and ongoing operation

Infrastructure and security approve the estate/key inventory. A screenshot or encrypted field alone is insufficient. Refresh on storage, key, provider or encryption changes; schedule periodic checks.

History and migration

Do not invent legacy consent times, rewrite existing clinical seals, or record mock authority responses as real acceptance.

Deployment

carejiox, carejiox_template, hhh — demo environments

Dependencies and claim limits

Technical acceptance does not replace policy approval, government decisions or clinic obligations.

Implemented control scope

Sensitive healthcare attachments use AES-256-GCM with transparent HTTP delivery and unchanged plaintext checksums. Scribe transcripts, correction reasons and AI coding payloads are encrypted; legacy plaintext columns are migrated without changing seals. Backup pairs use an external root-owned key.

Remaining acceptance and external work

Production disk/database encryption, independent key escrow, custody and rotation must be arranged. Existing PHI derivation is preserved; database.secret remains available to an authorised DB administrator.
